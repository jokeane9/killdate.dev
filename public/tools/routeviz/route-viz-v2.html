Visualization approaches for understanding your app

Different mental models surface different things. The right view depends on what question you're actually trying to answer — orientation, debugging, data, or deployment. Here's the honest tradeoff of each.

🗺
Route / URL map
What renders at each URL and what fires to get there
Best for: orientation

Pros

  • Maps to how users and browsers think — URLs not filenames
  • Auth model becomes instantly visible (who's gated where)
  • Parseable from file conventions alone — no deep analysis
  • Stays useful as codebase grows — doesn't get noisy

Cons

  • Doesn't show what data actually flows through loaders
  • Doesn't show component composition within a page
  • Misses dynamic routes and catch-all complexity
  • Framework-specific — doesn't generalize to all apps
When to use: first day on a codebase, debugging a redirect, understanding auth scope, pre-deploy blast radius check
↕
Data flow diagram
What each loader fetches, what actions mutate, where it goes
Best for: debugging

Pros

  • Shows where a bug lives — DB → loader → component → action
  • Makes useLoaderData vs useRouteLoaderData explicit
  • Reveals which routes share data vs fetch independently

Cons

  • Requires TypeScript type analysis or runtime tracing to build accurately
  • Goes stale fast — every loader change breaks the diagram
  • Gets noisy at scale — too many edges
  • Hard to generate statically, needs runtime instrumentation
When to use: "why is this component getting stale data", tracing a specific fetch, understanding shared state
🗄
Database schema / ER diagram
Tables, relationships, foreign keys
Best for: data model

Pros

  • 100% parseable from schema.sql or Prisma schema — no inference
  • Stable — schema changes less often than code
  • Prisma already does this reasonably well
  • Essential for writing queries correctly

Cons

  • Doesn't show which routes touch which tables
  • No information about query patterns or N+1 risks
  • Disconnected from the UI layer — you bridge it manually
When to use: writing a new query, understanding join paths, before a migration, explaining data model to a new hire
⚙
CI/CD pipeline graph
GitHub Actions jobs, dependencies, triggers, critical path
Best for: deploy

Pros

  • 100% parseable from YAML — no inference needed
  • Present in every repo regardless of language or framework
  • Job dependencies are exactly the kind of graph that needs visualization
  • Critical path analysis tells you where to optimize

Cons

  • GitHub already shows a basic version at runtime
  • Static view misses conditional logic and matrix builds
  • Less useful for small pipelines (2-3 jobs)
When to use: optimizing CI time, understanding what blocks a deploy, debugging a failed job, onboarding to a new repo's pipeline
🕸
Module dependency graph
Which files import which — coupling and shared code
Best for: refactoring

Pros

  • Reveals unexpected coupling between modules
  • Identifies shared utilities vs per-route code
  • Tools exist (Madge, dependency-cruiser)

Cons

  • Extremely noisy at any meaningful scale — unusable past ~30 files
  • All the existing tools have terrible UX
  • Not useful for orientation — too much detail, no hierarchy
  • Rarely the actual question you're trying to answer
When to use: pre-refactor audit, finding circular deps, understanding what breaks if you move a util file. Otherwise skip.

The right order for a dev getting oriented

1
Route map first. Understand the URL space, auth model, and which routes are layouts vs pages. 5 minutes, answers "how does navigation work and where do I start."
2
DB schema second. Read the tables and relationships. Understand the data model before reading any queries. 10 minutes, answers "what is this app actually storing."
3
Data flow on demand. Don't pre-read it. Pull it up when you hit a specific bug — "why is this loader getting null?" Trace that path specifically.
4
CI pipeline before first deploy. Know what gates exist, what can block a ship, and what the canary step is. One read, then you know.
5
Module graph almost never. Only if you're doing a major refactor and need to know blast radius. Otherwise the noise isn't worth it.
